# The edge, layer by layer

What the people building each layer are doing now, what it means for
fourneau, and the experiments it led to (numbers in the DIARY; the
experiments then lived in EXPERIMENTS.md). Read with the teaching manual
(the eldhus async-io skill), which explains the terms.

## Zig: std.Io

- `std.Io` is an interface like `Allocator`: `Io.Threaded` (a thread pool
  over blocking system calls) is the production implementation;
  `Io.Evented` (io_uring on Linux, GCD on macOS) runs code on fibers,
  stackful coroutines, and is **experimental**. [Kelley, "Zig's New Async
  I/O"](https://andrewkelley.me/post/zig-new-async-io-text-version.html);
  [devlog, 2026-02-13](https://ziglang.org/devlog/2026/).
- The devlog's list of follow-up work for Evented: error handling, the
  unexplained slowdown of evented mode, unimplemented functions, tests,
  and "a builtin function to tell you the maximum stack size of a given
  function to make these implementations practical". A stackless
  coroutine implementation may come later.
- Networking: Evented has none upstream. [Issue
  31723](https://codeberg.org/ziglang/zig/issues/31723) (open since
  2026-03-31): "std.Io.Evented is experimental, not intended to be used by
  non-contributors yet."

For fourneau: our vendored port (with networking) stays until upstream
serves. The stack-size builtin is the thing to watch: fiber locality
was our worst user-space cost (experiment 22), and exact-size stacks
would let fibers pack densely. Zig takes no LLM-assisted contributions,
so what we find (two compiler bugs, in TODO) the owner reports.

## Go

- No io_uring in the runtime. [golang/go#31908](https://github.com/golang/go/issues/31908),
  opened 2019, still "NeedsInvestigation". The obstacle is ownership:
  io_uring wants buffers handed over and pinned while an operation is in
  flight, and Go's model is any goroutine reading into any buffer, one
  operation at a time. Third-party pollers exist (cloudwego/netpoll).
- Measured here: Go net/http does 62k requests/s on one core, 44% of it
  kernel and the rest the runtime and handler.

## Rust: tokio, axum

- tokio's io_uring work is for **files**: [tokio#7266](https://github.com/tokio-rs/tokio/issues/7266)
  (2025), behind one global ring and a mutex in the unstable version
  ([discussion 7684](https://github.com/tokio-rs/tokio/discussions/7684)).
  Networking stays on epoll. tokio-uring, a separate runtime, is
  thread-per-core and slow-moving.
- Measured here: axum with TCP_NODELAY does 125k requests/s on one core;
  without it, pipelined requests stall 40 ms on Nagle (fourneau had the
  same bug, DIARY).

## Linux: io_uring

- Axboe's [networking guide](https://github.com/axboe/liburing/wiki/io_uring-and-networking-in-2023):
  `DEFER_TASKRUN` with `SINGLE_ISSUER` for busy servers (we use it: +5.5%);
  multishot accept and receive; provided buffer rings; `POLL_FIRST` for
  sockets known to be empty; no sharing of rings between threads (our
  shards don't); batching with `submit_and_wait`.
- Zero-copy receive (zcrx) landed in 6.15: a NIC queue DMAs payload into
  memory the application registered; 200 Gb/s from one core in Meta's
  demonstration ([Phoronix](https://www.phoronix.com/news/Linux-6.15-IO_uring),
  [LWN](https://lwn.net/Articles/965214/)). It needs a NIC with header
  split and flow steering, and a CVE (2026-43121) shows it is young. For
  small HTTP requests the copy is not the cost; for large uploads it
  could be. Later.
- Measured on fourneau-floor (raw io_uring, our own instrument):
  multishot receive and registered files are within noise for this
  workload; `POLL_FIRST` is 7% slower at saturation; linking each send to
  the next receive and skipping the send's completion is +15%.

## TigerBeetle

- Every object allocated at startup to a computed bound; each in-flight
  operation is an explicit struct in its owner, and completions are
  callbacks: a state machine, no fibers ([architecture](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/ARCHITECTURE.md)).
  io_uring for storage and network; deterministic simulation (VOPR).
- Measured here (experiment 3): the state machine costs 25% fewer
  cycles per request than fibers, with *more* instructions and a third
  of the cache misses. The hybrid (state machine for I/O, fibers only
  while a handler runs) is the open experiment that would test it in
  fourneau.

## Postgres 18

- Asynchronous I/O for reads, with `io_method` = `worker` (default,
  processes that block) or `io_uring`; io_uring is lower latency, workers
  win some scans with enough of them ([Freund, PGConf.EU 2025](https://anarazel.de/talks/2025-10-23-pgconf-eu-aio-in-PG-18-and-beyond/aio-in-PG-18-and-beyond.pdf),
  [Vondra](https://vondra.me/posts/tuning-aio-in-postgresql-18/)). The
  lesson for us: disk I/O wants batching and read-ahead, not one
  operation per wait. That is for SQLite (M5), not for the HTTP path.

## What it says about fourneau, measured

On one physical core, unpipelined (docs/benchmarks/2026-10-05-one-core.md
and later runs): fourneau ~300k requests/s, axum ~125k, Go ~62k; the
floor (raw io_uring) ~350-420k. The kernel is ~85% of fourneau's time,
so the kernel interface was the lever; user space is now ~2,000 cycles
per request against the floor's ~300, of which the fibers' locality was
the largest part we found.
