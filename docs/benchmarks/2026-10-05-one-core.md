# One physical core, every nanosecond charged

The method that replaces the six-core runs. On this laptop (i7-10510U, 4
cores, 8 hyperthreads) earlier benchmarks gave the server six hyperthreads
and the loader two, and the **loader was the limit**: the server's CPUs
sat half idle. Now the server gets one physical core (cpus 0-1) and the
loader the other three (2-7, six threads), and the server is charged every
nanosecond its two CPUs were not idle, from `/proc/stat`: user, system,
irq and **softirq**. Softirq is the kernel's network stack; it runs on the
server's CPUs but is never charged to its process, which is why
`/proc/PID/stat` showed the server "139% busy" when it was at 100%.

256 connections, `GET /` answering 13 bytes, 7 s runs measured over 4 s.

| server | pipeline | requests/s | user ns/request | kernel ns/request |
|---|---|---|---|---|
| fourneau (2 shards) | 1 | 269,194 | 835 | 6,621 |
| axum (TCP_NODELAY) | 1 | 125,466 | 4,861 | 11,058 |
| Go net/http | 1 | 61,587 | 18,104 | 14,166 |
| fourneau (2 shards) | 8 | 1,308,720 | 466 | 1,067 |
| axum (TCP_NODELAY) | 8 | 169,780 | 3,313 | 8,511 |
| Go net/http | 8 | 61,534 | 19,217 | 13,082 |

What it says:

- **The kernel is 89% of fourneau's cost** unpipelined. User space at
  835 ns is a small share; perfect user code would gain about 12%. Cache
  locality in user space is real (experiment 3) but it is not where the
  machine goes: the system calls and the TCP stack are.
- fourneau spends 40% less kernel time per request than axum (io_uring
  against epoll plus read/write calls) and 6x less user time.
- Pipelined, coalescing responses into one send (2026-10-05) took fourneau
  from one send per response to one per batch: 1.31M on one core.
